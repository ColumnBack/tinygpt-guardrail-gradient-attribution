모델은 왜 그 도구를 골랐을까?

NumPy로 직접 만든 작은 GPT를 MCP 도구 선택기로 학습시키고, 역전파(gradient)로 어떤 단어가 그 결정을 만들었는지 추적해 본 공부 노트입니다.

모든 숫자는 저장소의 코드를 실제로 실행해 얻은 값입니다 · 수식 노트: Interpretability math.pdf · GitHub 저장소

0진단 과정 한눈에: 오판 하나를 끝까지 따라가기

모델이 틀렸을 때 원인을 찾는 과정을 일곱 단계로 따라갑니다. 각 단계는 질문 하나 → 기법 하나 → 답 하나입니다. 아래 단계를 누르거나 ← → 키로 넘겨 보세요. 자세한 설명은 이어지는 1~8번 섹션에 있습니다.

1모델이 도구를 고르는 방식

문장 끝에 <call> 표시를 붙이고, 그 위치에서 "다음에 올 단어"를 예측하게 합니다. 그 다음 단어가 곧 도구 이름입니다. 학습할 때도 이 한 자리에만 정답을 알려 줍니다(masked loss).

도구 10개(파일 읽기·쓰기·목록, 웹 검색·가져오기, 날씨, 일정, 메일, DB, git) 중 확률이 가장 높은 것을 고릅니다. 학습에 없던 동사·목적어 조합 60문장을 모두 맞혔습니다.

2역전파로 단어별 점수 구하기

학습할 때와 같은 역전파를 쓰되 두 가지만 바꿉니다: loss 대신 점수 S = Z[<call>, y](출력 토큰 y = 도구의 logit 하나)를 미분하고, 파라미터가 아니라 입력 단어 임베딩까지 내려가서 멈춥니다. 순서는 ∂S/∂Z → ∂S/∂H → ∂S/∂X입니다.

forward: 단어 → 점수 backward: 점수 → 단어 (∂S/∂X) 
# tool_attribution.py · score_and_grad
logits, _, caches = model.forward_embedded(X_token)   # ① forward (임베딩부터)
G[k, y] = 1                                            # ② ∂S/∂Z :  S = Z[k, y]
GX = G @ E                                             # ③ ∂S/∂H  (Z = H·Eᵀ)
for n in reversed(range(N)):                           # ④ 블록을 거꾸로
    GX, _ = model.block_backward(GX, caches[n], n)     #    (파라미터 기울기는 버림)
return s, GX                                           # ⑤ ∂S/∂X : 단어마다 벡터 하나

3같은 기울기, 네 가지 점수

∂S/∂X는 단어마다 64차원 벡터입니다. 이것을 단어마다 숫자 하나로 줄이는 방법이 여러 가지이고, 결과가 꽤 다릅니다. 예문 → , 점수 S = Z[<call>, 선택 도구].

선택한 도구 쪽으로 미는 단어 (+) 반대쪽으로 미는 단어 (−)
눈여겨볼 곳: html은 grad×input이 로 작지만, IG는 로 가장 큽니다. 한 점의 기울기(국소)만 보면 놓치는 기여를, 경로 전체를 적분하는 IG는 잡아냅니다.

4IG(Integrated Gradients) 직관

단어 임베딩을 0(기준점)에서 실제 값까지 조금씩 키우면서(α: 0→1), 매 순간의 기울기를 모아 더합니다. 슬라이더를 움직여 보세요. 막대는 α까지 쌓인 IG, 아래 곡선은 그 순간의 점수입니다.

completeness: 모든 단어의 IG를 더하면 언제나 S(입력) − S(기준점)과 같습니다. 점수 변화 전체를 단어들에게 남김없이 나눠 준다는 뜻이고, 이 값이 맞지 않으면 적분 단계가 부족한 것입니다.

5포화 함정: 확률을 그대로 미분하면 0이 나온다

모델이 확신할수록 확률이 1에 붙어 버려, 기울기가 사실상 0이 됩니다. 그러면 "아무 단어도 중요하지 않다"는 엉뚱한 결론이 나옵니다.

점수 = log P(도구)

log P = (P ≈ 1)

점수 = Z[<call>, 도구] (logit)

softmax를 거치지 않은 logit이라 포화가 없습니다.

막대 길이는 단어별 기울기 크기 |∂S/∂x|입니다. 왼쪽은 값이 1e-6 수준이라 막대가 보이지 않습니다.

6긴 문장 디버깅: 단어 하나 바꿨더니 틀린다

실제 요청 로그처럼 "상황 설명 + 요청" 형태의 긴 문장으로 학습했습니다. 상황 설명 30개는 모든 도구가 공유하고, 주제가 맞는 도구와 약 70%만 같이 나옵니다. 정확도는 괜찮아 보이는데, 정말 요청을 보고 고르고 있을까요?

7층과 경로로 따라가기: hidden state · attention · occlusion

IG는 "어떤 단어"를 알려 줍니다. 같은 draft 오판을 세 가지 다른 기법으로 다시 보면, 그 단어가 몇 번째 층에서, 어떤 경로로 결정을 뒤집었는지까지 보입니다. A = the server … (정답 ), B = the draft … (오답 ).

1

층별 hidden state 차이: 차이는 어디서 시작해 어디로 퍼지나

칸의 진하기 = ‖hB − hA‖ / ‖hA‖. embed 단계에서는 바뀐 단어 칸만 차이가 있고, 층을 지날수록 attention이 그 차이를 다른 위치로 옮깁니다. 테두리 칸이 결정 위치 <call>입니다.

2

logit lens: 몇 번째 층부터 오답 쪽인가

각 단계의 <call> hidden state를 출력층에 바로 통과시킨 값입니다. 0보다 크면 정답 도구가 앞섭니다. 중간층은 출력용으로 학습되지 않았으므로 근사적인 보기입니다.

A (정답 문장) B (오답 문장) 값 = z[정답 도구] − z[오답 도구]

B는 1층을 지나도 정답 쪽이고, 2층 attention에서 오답으로 넘어갑니다.

3

attention: 2층에서 <call>은 어디에서 정보를 가져오나

칸의 진하기 = norm 기반 기여도 ‖Σh A[k,j] · V[j] WO‖ (가중치 × 그 단어가 보내는 값의 크기). 가중치만 보면 "많이 봤지만 영향은 작은" 단어를 구별할 수 없어서 norm을 씁니다.

4

occlusion: 지워 보면 확인된다

B에서 단어를 하나씩 0으로 지우고, 오답 도구 점수 Z[<call>, 오답]이 얼마나 떨어지는지 직접 쟀습니다. 가장 큰 원인은 IG와 같지만, 작은 기여는 서로 다르게 봅니다(하나만 지운 효과 vs 경로 적분).
